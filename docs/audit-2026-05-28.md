## relevance (econsignals/lib/relevance.py)  — **broken**

The scorer is dominated by signals unrelated to topical fit: author proximity (0.25 weight) fires at 0.7 for nearly every OpenAlex paper because 1185 authors are flagged auto_discovered with 0 tracked, while the intended primary signal (JEL, 0.30 weight) is dead for 97% of papers (only 21/569 have JEL codes). The result is a ~0.43-0.50 floor for any recent paper with an auto-discovered author and any India token, regardless of subject, which is exactly why a Norwegian next-of-kin study and a crypto-regulation paper top the list. Fix is to make keyword/JEL fit the dominant term, neutralize auto_discovered author credit, and gate the India boost on topical relevance.

### [critical/high] Author proximity (0.25 weight) credits every OpenAlex paper because 1185 authors are auto_discovered and 0 are tracked
- **Evidence:** relevance.py:256-319 returns 0.7 for any auto_discovered author. DB: SELECT total_authors, SUM(is_tracked), SUM(auto_discovered) FROM authors -> 6046, 0, 1185. All 9 top-scored papers have 0 tracked but 1-5 auto_discovered authors (paper ids 74,98,101,...), contributing _W_AUTHOR*0.7 = +0.175 each. With JEL dead, author proximity is the single largest contributor to the top ranks and is pure noise (the user has tracked nobody).
- **Root cause:** auto_discovered is set indiscriminately by the OpenAlex sensor (1185 authors), so the 0.7 tier is not a proximity signal at all. The composite weights a noise channel at 0.25, second only to JEL.
- **Fix:** Stop crediting auto_discovered at 0.7 when there are no tracked authors to be 'near'. In score_author_proximity, return 0.0 for the auto_discovered tier unless a tracked-author graph exists (e.g. `if auto_disc and _has_tracked_authors(db): best = max(best, 0.3)`), and drop the per-author 0.7 to 0.3. Better: reallocate the freed weight to topical fit. Change weights to _W_JEL=0.22, _W_KW=0.33, _W_AUTHOR=0.10, _W_PRESTIGE=0.10, _W_RECENCY=0.08, _W_SOCIAL=0.02 (sum 0.85; India handled separately, see below). With 0 tracked authors the author term is ~0 for everyone, so it stops distorting ranks.

### [critical/high] JEL is the largest weight (0.30) but only 3.7% of papers have JEL codes, so the primary topical signal is null for the corpus
- **Evidence:** relevance.py:32 _W_JEL=0.30. DB: 21/569 papers have non-empty jel_codes; the other 548 get score_jel=0.0 (relevance.py:204-205). 389 papers cluster at 0.1 and the whole distribution compresses below 0.4 (only 16 >=0.4). score_jel returns 0.0 (not _default) when jel_codes is empty, so missing-JEL papers get zero, not the 0.1 floor.
- **Root cause:** The design assumed JEL codes would be populated; the dominant sensors (crossref, iza, openalex) supply almost none. A 0.30 weight on a field that is empty 96% of the time means topical relevance is decided by the 0.20 keyword term alone, which itself is broken (see next).
- **Fix:** Two-part: (a) lower _W_JEL to ~0.22 and raise keyword weight as above; (b) when jel_codes is empty, derive pseudo-JEL relevance from the keyword/title match rather than returning 0.0, OR fold JEL and keywords into one 'topical fit' term so a paper is not penalized to zero for a metadata gap the pipeline cannot fill. Minimum viable: in score_paper, if not jel_codes, set s_jel = s_kw so the JEL weight rides on keyword evidence instead of contributing 0.

### [high/high] Keyword score denominator is all 35 keywords, capping a perfect on-topic paper at ~0.26 and rewarding generic-word false positives
- **Evidence:** relevance.py:252-253 score = matches/len(interest_kw) with len=35. Verified: a strong India-urban title hitting 9 keywords scores 0.257; an off-topic 'Human capital and public markets: a finance perspective' scores 0.114 purely from generic tokens. interest_kw includes single generic words ('public','goods','human','capital','markets','use','cities','economic','policy') that match unrelated finance/CS/health papers.
- **Root cause:** Dividing by total keyword count means no paper can hit a large fraction (no paper is about all 35 topics), so the strongest topical signal saturates around 0.25-0.30. Splitting comma-separated phrases into single tokens (relevance.py:170-175) destroys multi-word concepts ('land use','property rights','informal sector','smart cities') and creates high-frequency generic unigrams.
- **Fix:** (1) Preserve multi-word phrases as bigrams: in load_interest_keywords keep the full comma-delimited phrase ('property rights') and substring-match it against combined text, not split on whitespace. (2) Change denominator from len(interest_kw) to a saturating function: `min(1.0, matches / 3.0)` so 3+ topical hits = full score. (3) Drop bare generic unigrams ('human','capital','public','goods','use','economic') from the matchable set or require they appear inside a tracked phrase. Net effect: a genuine India-dev-urban paper reaches ~1.0 on the keyword term, a finance paper stays near 0.

### [high/high] India boost is a flat +0.15 on any 'india' token anywhere, with no topical gate
- **Evidence:** relevance.py:482-522 returns +0.15 if _INDIA_PATTERNS matches title/abstract/affiliation. The #1-tier list includes 'CRYPTOCURRENCY REGULATION ... India' (0.498) and 'EMERGING TRENDS ... COFFEE CONSUMPTION IN INDIA' (0.481): both get the full boost despite being off-field. DB: 29 papers mention india in title/abstract; the boost is what lifts them above the pack.
- **Root cause:** The boost is additive and unconditional, so it rewards geography independent of field. For a dev/urban-India economist the relevant signal is India AND (dev/urban/labor/public), not India alone. An unconditional +0.15 also lifts off-topic India papers above on-topic non-India papers (e.g. a top-5-journal urban paper on Lagos).
- **Fix:** Make the India boost multiplicative on topical fit instead of additive: `boost = _INDIA_BOOST * max(s_jel, s_kw)` so India only amplifies papers that already show field relevance. Or gate it: only apply +0.15 if (s_jel + s_kw) exceeds a small threshold. This drops the crypto/coffee/India papers while preserving genuine India-dev papers. Implement in score_paper around line 568-579.

### [medium/high] Recency adds up to +0.10 to every fresh item and future-dated papers all score 1.0, inflating the noise floor
- **Evidence:** relevance.py:403-437. DB published_at distribution shows 2026-12 (50), 2027-01 (31), 2028-01 (11), 2030-01 (6): future dates yield negative age_days, hit the age<=7 branch, return recency=1.0. Every top paper is dated 2026-12 and gets _W_RECENCY*1.0=+0.10. Recency rewards arrival time, not relevance, and currently lifts the entire recent cohort uniformly so it cannot separate signal.
- **Root cause:** No clamp on future dates, and recency weight (0.10) is comparable to the entire topical contribution for JEL-less papers, so freshness swamps fit. The score_all_papers window is days=30/7 yet papers carry far-future dates, so the recency term is effectively a constant +0.10 across the rankable set.
- **Fix:** Clamp future dates: in score_recency, `if age_days < 0: age_days = 0` (treat as today, not better-than-today). Lower _W_RECENCY to 0.08 and let recency break ties only. Separately, the sensor should not be ingesting 2030-dated papers; validate published_at <= today+1 at ingest. The clamp is the one-line relevance-side fix.

### [medium/medium] Unknown-source and missing-date defaults (0.3 and 0.5) manufacture a high baseline that compresses the distribution
- **Evidence:** relevance.py:344 returns 0.3 prestige for unknown source; line 420 returns 0.5 recency for unknown date; openalex prestige defaults 0.5 (line 64). A paper with no JEL, no real author tie, generic source gets _W_PRESTIGE*0.5 + _W_RECENCY*(0.5-1.0) = 0.05-0.10 of 'free' score. Combined with the auto_discovered author tier this is why 389 papers pile at exactly 0.1 and the usable range is only 0.1-0.5.
- **Root cause:** Neutral defaults set high (0.3-0.5) on multiple channels add a constant offset to nearly every paper, shrinking the dynamic range so true relevance differences (which live in the dead JEL/weak keyword terms) cannot move ranks.
- **Fix:** Lower neutral defaults: unknown source prestige 0.3 -> 0.15 (line 344), unknown date recency 0.5 -> 0.2 (line 420), openalex generic 0.5 -> 0.3 (line 64). This widens the gap between topical and non-topical papers without touching the weights.

### [low/medium] Zenodo/OSF downweight only fires when source_url contains the host, but raw_metadata also encodes Zenodo and is not checked for the cap
- **Evidence:** relevance.py:357-361 caps prestige only via source_url string match. The #1 paper (id 74) is a Zenodo DOI; source_url IS 'doi.org/10.5281/zenodo...' so the cap should fire to 0.1, yet the reconstructed score matches prestige=0.5, indicating the cap is being overridden by the per-row max with the openalex src_score on a second source row, or the 'doi.org' URL masks the 'zenodo.org' substring test (the URL contains 'zenodo' but not 'zenodo.org').
- **Root cause:** The substring test is `'zenodo.org' in source_url` but the stored URL is a doi.org redirect ('https://doi.org/10.5281/zenodo.18251233'), which contains 'zenodo' but not 'zenodo.org', so the cap never applies to DOI-form Zenodo links.
- **Fix:** Change the test to `'zenodo' in source_url` (line 359) and add the raw_metadata host check (primary_location.source.display_name often = 'Zenodo'). This pushes preprint-mill Zenodo items down where they belong.

**Recommendations:**
- (M) Collapse JEL + keyword into one topical-fit term that degrades gracefully when JEL is absent, then make it the dominant weight (~0.55 combined). Concretely: s_topic = max(s_jel, s_kw_phrase) with phrase-based keyword matching and a min(1, hits/3) saturation; weight it 0.50-0.55. — The corpus has near-zero JEL coverage (3.7%) but rich titles/keywords (365 papers have keywords). Today the two topical channels together carry 0.50 weight but deliver almost nothing because JEL is empty and keywords saturate at 0.26. Merging and saturating them is the single change that lets India/dev/urban papers actually rise.
- (M) Add an acceptance test: tests/test_relevance_ranking.py that scores the current 569-paper corpus and asserts (a) at least 12 of the top 20 match India|development|urban|labor|public via JEL prefix in {O,R,I,J,H} OR title regex for dev/urban India terms, and (b) the crypto/coffee/Norwegian-next-of-kin papers fall out of the top 50. Run before/after the reweighting to prove separation. — The owner abandoned the tool because output quality was unverifiable. A corpus-level ranking test turns 'feels better' into a pass/fail gate and prevents regression when weights are next touched.
- (S) Neutralize the auto_discovered author tier until tracked authors exist: return 0.0 (or <=0.3 gated on a tracked-author graph) and reclaim that 0.25 weight for topical fit. — 1185 auto_discovered / 0 tracked means the 0.25 author channel is pure noise that currently decides the top ranks. With no tracked authors the term should contribute nothing, not 0.175 per paper.
- (S) Make the India boost multiplicative on topical fit (_INDIA_BOOST * max(s_jel, s_kw)) and clamp future publication dates in score_recency. — Both are one-to-three-line changes that directly remove the two visible failure modes: off-topic 'India' papers topping the list, and future-dated 2027-2030 papers all scoring recency=1.0.

**External patterns:**
- Semantic Scholar Research Feeds: builds a per-user relevance vector from a small set of explicitly liked 'seed' papers and ranks new arrivals by embedding cosine similarity to that vector, with continuous thumbs-up/down updating the vector (an SVM-style boundary in embedding space). Lesson for EconSignals: replace the brittle 35-keyword bag and dead JEL channel with similarity to a handful of the owner's own India-dev-urban papers; this is what makes a perfect-fit paper rank high without depending on JEL metadata the pipeline never gets.
- Semantic Scholar separates topical relevance from a small recency/novelty nudge rather than additively summing them, so freshness only re-orders among already-relevant items; mirror this by making recency a tie-breaker (low weight, clamped), not an additive lift to every fresh paper.
- scite / scite Assistant ranks by citation-context quality (supporting vs contrasting citations) and venue trust rather than recency, explicitly down-weighting preprint-mill and predatory sources. Lesson: extend the Zenodo/OSF downweight into a venue-trust tier and consider a citation-velocity signal so genuinely impactful working papers rise above high-volume low-signal OpenAlex dumps.
- scite and Semantic Scholar both normalize scores per-cohort (rank/percentile within the day's batch) before presenting, avoiding the fixed-threshold compression EconSignals suffers; a percentile transform over the scored batch would restore dynamic range even before the weight fixes land.


## dedup (lib/dedup.py + author upsert/link + newsletter author rendering)  — **broken**

The visible "Erna Henriette Dahl Tyskø, Erna Henriette Dahl Tyskø" bug is real and systemic: the same author is stored as many separate rows (one per source, since affiliation differs or is NULL) and ALL of them get linked to the same paper, so the newsletter renders the name once per row. Root cause is a SQLite UNIQUE/ON CONFLICT mismatch — UNIQUE(name_normalized, affiliation) treats NULL affiliation as distinct, so the upsert never deduplicates the 5953/6046 NULL-affiliation rows. 6046 author rows collapse to only 1208 distinct names; some authors exist in 26-27 copies. The dedup cascade itself (DOI→title→Jaccard→author-overlap) is mostly sound but has secondary precision bugs.

### [critical/high] Author upsert never dedups NULL-affiliation rows: UNIQUE(name_normalized, affiliation) + ON CONFLICT is a no-op when affiliation IS NULL
- **Evidence:** db.py:380-435 upsert_author uses ON CONFLICT(name_normalized, affiliation). DB: SELECT COUNT(*) authors=6046 but COUNT(DISTINCT name_normalized)=1208. 5953 rows have NULL affiliation. sensor_runs shows openalex ran 13x, crossref 13x — each re-run re-inserts the same NULL-affiliation authors.
- **Root cause:** SQLite treats NULL as distinct in UNIQUE indexes, so two rows with the same name_normalized and NULL affiliation do NOT violate UNIQUE(name_normalized, affiliation), and the ON CONFLICT(name_normalized, affiliation) clause in upsert_author never fires. Every re-ingestion of an author without an affiliation inserts a brand-new row. Verified empirically: in-memory test inserting ('x', NULL) twice with this exact ON CONFLICT leaves 2 rows. DB confirms 5953/6046 author rows have NULL affiliation; name_normalized 'cervera-marzal manuel' has 27 rows, 'abdul rahim abdul samad' 26 rows.
- **Fix:** Make NULL affiliations collapse. Either (a) store affiliation as '' (empty string) instead of NULL — change upsert_author to `affiliation = kwargs.get('affiliation') or ''` and backfill existing NULLs (UPDATE authors SET affiliation='' WHERE affiliation IS NULL), since SQLite DOES dedup on equal empty strings; or (b) drop affiliation from the dedup key entirely (UNIQUE(name_normalized)) and treat affiliation as a mergeable attribute, which matches the actual intent (one author = one identity regardless of affiliation variation across sources). Option (b) is correct for this domain — an author is the same person whether or not a source reports affiliation. With (b), also merge affiliation via COALESCE in the ON CONFLICT SET clause. The find-back query at db.py:431 ('WHERE name_normalized = ? AND affiliation IS ?') must change to match the new key.

### [critical/high] link_paper_author links every duplicate author row to the paper, producing N copies of the same name at the same position
- **Evidence:** DB: paper_id 548 has author_id 5797 (Tyskø, affiliation NULL, position 0) AND author_id 5798 (Tyskø, Western Norway, position 0) — both name 'Erna Henriette Dahl Tyskø'. paper_id 97 has 'Gopagalla hruthik' 3x (ids 362,366,428 all position 1). Newsletter render query returns both → 'Tyskø, Tyskø'. This is the reported bug exactly.
- **Root cause:** Because upsert_author returns a different author_id for each duplicate row, ingest_paper (dedup.py:556-561) calls link_paper_author once per source-version of the author and the paper_authors PRIMARY KEY (paper_id, author_id) does NOT dedup them — the author_ids differ. So the same person ends up linked twice (or more) to one paper, all at position 0. get_recent_papers (db.py:720-730) returns both rows ordered by position, and newsletter _author_str (newsletter.py:150-162) joins them verbatim.
- **Fix:** Primary fix is to dedup authors (bug #1) so only one author_id exists per person. Defense-in-depth at render: in db.py get_recent_papers/get_paper author query, dedup by author identity, e.g. `SELECT a.id, a.name, a.affiliation, MIN(pa.position) position FROM authors a JOIN paper_authors pa ON pa.author_id=pa.author_id WHERE pa.paper_id=? GROUP BY a.name_normalized ORDER BY position`. And in _author_str (newsletter.py:150), dedup the name list while preserving order before joining: `seen=set(); names=[n for n in names if not (n.lower() in seen or seen.add(n.lower()))]`.

### [high/high] _strip_accents drops non-decomposable Unicode letters (ø, đ, ł, ß) instead of transliterating, mangling names and titles
- **Evidence:** Verified: unicodedata.normalize('NFKD','Tyskø').encode('ascii','ignore').decode() == 'Tysk' (ø vanished). normalize.py:17-19. DB authors.name_normalized for both Tyskø rows = 'erna henriette dahl tysk'.
- **Root cause:** normalize.py:19 uses unicodedata.normalize('NFKD', s).encode('ascii','ignore') which silently DELETES any codepoint with no ASCII decomposition. 'Tyskø' → 'tysk', 'Łukasz' → 'ukasz', 'Weiß' → 'wei'. This corrupts name_normalized and title_normalized, degrading dedup matching (two spellings of the same Scandinavian/Polish/German name normalize differently than a clean ASCII source would) and is why the stored normalized form is 'erna henriette dahl tysk'.
- **Fix:** Replace the lossy ASCII drop with a transliteration that preserves a letter. Minimal: add an explicit map before encoding — `s = s.translate(str.maketrans({'ø':'o','Ø':'o','đ':'d','ł':'l','ß':'ss','æ':'ae','œ':'oe'}))` then NFKD+ascii-ignore. Better: use the `unidecode` library if available (unidecode('Tyskø')=='Tysko'). Re-normalize existing authors/papers after the fix.

### [medium/medium] Fuzzy-title cascade (step 3) returns first candidate over 0.85 instead of the best, and includes stopwords in token set
- **Evidence:** dedup.py:312-318 (returns on first match). normalize.py:210-226 title_token_set = set(normalize_title(title).split()) with no stopword removal; normalize_title docstring example keeps 'and'. DB shows exact-title collisions exist ('quality upgrading in global supply chains evidence from colombian coffee' x2) that step-2 multi-match handles, but fuzzy variants would not be caught reliably.
- **Root cause:** dedup.py:315-318 iterates LIKE candidates and returns the FIRST whose Jaccard >= 0.85, not the maximum-scoring one — non-deterministic by DB row order, can merge into the wrong paper when several near-duplicates exist. Separately, title_token_set (normalize.py:226) keeps stopwords ('and','the','of'), inflating union size and depressing Jaccard so genuine duplicates that differ by a subtitle can fall below 0.85 (false split).
- **Fix:** In step 3, collect all candidates and return argmax: `best=max(((jaccard_similarity(tokens, title_token_set(r.get('title',''))), r['id']) for r in cands), default=(0,None)); if best[0]>=_JACCARD_FUZZY_THRESHOLD: return best[1]`. Add a small stopword set to title_token_set (drop {'a','an','the','and','of','in','on','for','to','from','with','evidence'}) to sharpen Jaccard.

### [medium/medium] paper_sources re-inserts duplicate (source, source_id) on every scan, and 78 papers have zero linked authors
- **Evidence:** DB: paper_sources paper_id=183 → 4x crossref, 90 → 3x openalex. papers=569, COUNT(DISTINCT paper_id) in paper_authors = 491 → 78 author-less papers.
- **Root cause:** paper_sources has UNIQUE(source, source_id) but ingest_paper calls insert_paper_source unconditionally on every re-ingest; if insert_paper_source uses INSERT OR IGNORE this is harmless, but DB shows paper_id 183 with 4 identical 'crossref' rows and paper 90 with 3 'openalex', meaning source_id varied or the UNIQUE isn't enforced on that path. Separately 78 of 569 papers (569 total vs 491 with any author) have NO authors — these render with the '(authors unknown)' fallback, a quality gap.
- **Fix:** Audit insert_paper_source for INSERT OR IGNORE / ON CONFLICT(source,source_id) DO NOTHING. For author-less papers, have sensors populate authors before ingest or backfill from raw_metadata. Lower priority than #1/#2.

**Recommendations:**
- (M) Fix bug #1 (author dedup key) and #2 (render dedup) together, then run a one-time migration: merge duplicate author rows by name_normalized, repoint paper_authors.author_id to the surviving id, delete orphans, and de-duplicate paper_authors. — These two are the entire visible failure. Without the migration the 6046→1208 collapse won't happen retroactively and the newsletter keeps showing doubled names.
- (S) Add a unit test that ingests the same author twice (once with affiliation, once without) and asserts paper['authors'] has exactly one entry for that person. — The smoke-test in dedup.py:570-799 only tests title/DOI merge, never author duplication — which is why this shipped. A regression test pins the fix.
- (S) Fix _strip_accents transliteration (bug #3) and re-normalize the authors and papers tables. — Improves dedup recall for non-English names (relevant: India-focused profile still ingests global co-authors) and stops storing mangled normalized forms.
- (S) Make the dedup cascade deterministic (argmax in step 3) and add stopword stripping to title_token_set. — Removes a non-determinism that can cause wrong-paper merges and reduces false splits on subtitle variants.

**External patterns:**
- OpenAlex/Crossref model authors as stable entities keyed by external ID (openalex_id/ORCID), not by (name, affiliation); EconSignals already stores these columns but the upsert key ignores them — keying on a coalesced external ID when present would dedup correctly across sources
- Zotero/reference managers store one creator record and treat affiliation as paper-scoped metadata, not part of author identity — matches recommended fix (b) for bug #1

### [high/high] Bluesky sensor produces zero rows: needs auth for search and has no tracked authors with handles
- **Evidence:** sensor_runs shows bluesky ran 6 times with status=success but social_items has 0 bluesky rows. DB: SELECT COUNT(*) FROM authors WHERE bluesky_handle IS NOT NULL AND trim(bluesky_handle)<>'' returns 0. bluesky.py:369-374, 418-425.

## db (econsignals/lib/db.py — schema + persistence)  — **broken**

The persistence layer has two data-proven upsert bugs where NULL columns defeat UNIQUE/ON CONFLICT dedup (5306 duplicate author rows; 420 duplicate/invisible funding deadlines) and a timestamp-format mismatch that silently drops the newsletter's freshest papers. Connection cleanup was fixed in only 1 of 17 functions, leaving WAL-lock leaks (reproduced live as "database is locked"). ### [critical/high] upsert_author duplicates every NULL-affiliation author on every run (NULL defeats UNIQUE/ON CONFLICT)
- **Evidence:** authors table: 6046 rows but only ~1208 distinct NULL-affiliation names; 5953 NULL-affiliation rows, of which 5306 are pure duplicates. Single names repeated 26x ('ben seyd', 'bin zhao', etc. — one copy per sensor run). Query: SELECT name_normalized,count(*) FROM authors WHERE affiliation IS NULL GROUP BY name_normalized HAVING count(*)>1 returns names with c=26.
- **Root cause:** authors has UNIQUE(name_normalized, affiliation) (db.py:79) and upsert_author uses ON CONFLICT(name_normalized, affiliation) (db.py:403). In SQLite, NULLs are distinct in a UNIQUE index, so when affiliation IS NULL the conflict never fires: the INSERT always creates a new row and the DO UPDATE branch never executes. The trailing 'SELECT id ... WHERE name_normalized=? AND affiliation IS ?' (db.py:430-433) then returns multiple rows and fetchone() picks an arbitrary one, so callers in dedup.py get a non-deterministic author_id and link papers (paper_authors) to whichever duplicate happened to exist at ingest time.
- **Fix:** Make affiliation NOT NULL DEFAULT '' (treat 'no affiliation' as empty string, never NULL) so the UNIQUE constraint and ON CONFLICT target actually dedupe. Migration: UPDATE authors SET affiliation='' WHERE affiliation IS NULL; then dedupe (keep MIN(id) per (name_normalized,''), repoint paper_authors.author_id, delete the rest); then rebuild the UNIQUE index. In upsert_author, coalesce at the boundary: affiliation = kwargs.get('affiliation') or ''. Also add ORDER BY id LIMIT 1 to the trailing SELECT so id resolution is deterministic even if dup rows linger.

### [critical/high] get_recent_papers drops the cutoff-day papers (incl. today's) due to first_seen_at format mismatch
- **Evidence:** Proven against live DB: WHERE first_seen_at >= '2026-03-12T00:00:00Z' returns 0; WHERE first_seen_at >= '2026-03-12 00:00:00' returns 25; rows actually on 2026-03-12 = 25. Python: '2026-03-12 05:17:00' >= '2026-03-12T05:17:00Z' is False.
- **Root cause:** first_seen_at is written by SQLite DEFAULT (datetime('now')) which produces 'YYYY-MM-DD HH:MM:SS' (space separator, no Z). get_recent_papers builds its cutoff with strftime('%Y-%m-%dT%H:%M:%SZ') -> 'YYYY-MM-DDTHH:MM:SSZ' (T separator, Z suffix) (db.py:702-704). The WHERE first_seen_at >= cutoff is a lexicographic string compare; for any row whose date equals the cutoff date, the space char (0x20) sorts BEFORE 'T' (0x54), so the row is rejected. For days=1 the cutoff date is today, so all of today's freshly-ingested papers are excluded — the core purpose of a daily newsletter.
- **Fix:** Make the storage and query formats identical. Simplest: build the cutoff with the same space format SQLite uses: cutoff = (datetime.now(timezone.utc) - timedelta(days=days)).strftime('%Y-%m-%d %H:%M:%S') in get_recent_papers (db.py:702-704). Better long-term: store first_seen_at via the app's _now_iso() (consistent 'T...Z') by changing the column default and the INSERT, so all timestamps share one format; then keep the Z-format cutoff. Pick one format repo-wide.

### [high/high] upsert_deadline duplicates rolling (NULL-date) deadlines and they are invisible to the newsletter
- **Evidence:** deadlines: 441 rows, 419 of 431 funding rows have NULL deadline_date; 420 NULL-date rows collapse to only 80 distinct names (one name has 23 copies). The priority funding set the whole tool targets (PEDL/STEG/IGC/J-PAL) is exactly the rolling-deadline class being lost.
- **Root cause:** Same NULL-defeats-UNIQUE root cause as the author bug. deadlines has UNIQUE(name, deadline_date) (db.py:113) and upsert_deadline uses ON CONFLICT(name, deadline_date) (db.py:539). Funding sensors deliberately insert rolling deadlines with deadline_date=None (funding.py:379-421). With deadline_date NULL the conflict never fires, so every scan re-inserts the row. Separately, get_upcoming_deadlines filters WHERE deadline_date >= today AND <= cutoff (db.py:585-588), which NULL never satisfies, so every rolling funding deadline is silently dropped from the brief.
- **Fix:** Two changes. (1) Dedup key: give rolling deadlines a stable non-NULL key. Either store a sentinel (deadline_date='') or add UNIQUE on a stable column (e.g. url or a (type,name,organization) tuple) and target that in ON CONFLICT. (2) Query: in get_upcoming_deadlines, include rolling deadlines: WHERE (deadline_date IS NULL OR (deadline_date >= ? AND deadline_date <= ?)) and sort with NULLs last (ORDER BY deadline_date IS NULL, deadline_date ASC). Migrate existing dupes first (keep MIN(id) per name).

### [high/high] 16 of 17 DB functions leak the connection on exception; only insert_paper has try/finally
- **Evidence:** Reproduced live: two of my read-only count queries failed with 'database is locked (5)' and 'unable to open database file (14)' — the exact symptom of leaked write connections holding WAL/SHM locks. grep confirms only insert_paper uses try/finally.
- **Root cause:** The earlier leak fix (commit c16d083, the only commit touching db.py) was applied to insert_paper alone (try/finally, db.py:248-281). Every other function opens conn=get_db() and calls conn.close() as a plain trailing statement (e.g. find_paper_by_doi db.py:293-295, get_tracked_authors:464-468, insert_social_item:487-509, log_sensor_start:617-628, get_recent_papers:706-734, get_paper_with_sources — which even has an early raise KeyError that DOES close, but the rest do not). ## zotero-personalization  — **broken**

The embedding path runs (Ollama + nomic-embed-text is actually pulled, contra the briefing) but produces near-uniform scores: it averages cosine similarity over all 495 econ-Zotero items, so the high baseline similarity floor swamps the signal and an off-topic protein-folding paper scores 4.33 vs an on-topic Mumbai-zoning paper at 5.35. Recency weighting is doubly dead (all dates parse to datetime.min from a format bug, and the decay curve is near-flat anyway), and the caller never falls back to lexical when embeddings silently return zeros. This near-constant ~0.5 boost added to every paper is the root cause of the "poor output quality" that got the tool abandoned.

### [critical/high] Mean-pooled similarity over the whole homogeneous corpus washes out the personalization signal
- **Evidence:** Live test on real corpus (cache at data/zotero_embedding_cache.pkl): 'Deep learning for protein folding' mean=0.431, 'Misallocation in Indian agriculture' mean=0.521, 'Zoning in Mumbai' mean=0.538 — a 0.06-0.11 spread. Same candidates by top5-mean: 0.536 vs 0.705 vs 0.742; by max: 0.568 vs 0.723 vs 0.762 — a 0.19 spread, ~3x the separation. Caller (newsletter.py:237) does zotero_boost=min(score/10,0.7), yielding 0.43-0.54 for ALL papers — a near-constant offset, not a ranking signal.
- **Root cause:** compute_zotero_embedding_scores computes a weighted AVERAGE of cosine similarity across ALL ~495 corpus items (zotero_embeddings.py:177-178: scores = (sim * time_decay).sum(axis=1)). Because the entire Zotero library is econ papers, every candidate (even off-topic) has a high mean cosine floor (~0.43-0.54). The discriminating signal lives in the MAX / top-k similarity to the most-related items, which averaging discards.
- **Fix:** Replace the corpus-wide weighted mean with top-k pooling. In zotero_embeddings.py:171-178, drop the time_decay path and compute per-candidate: `k=min(8,sim.shape[1]); topk=np.sort(sim,axis=1)[:, -k:]; scores=topk.mean(axis=1)*scale`. Then rescale the caller: scores now ~0.5-0.78, so newsletter.py:237 becomes `zotero_boost = max(0.0, min((score/scale - 0.45)/0.35, 0.7))` (subtract the ~0.45 floor before scaling so the boost reflects relative, not absolute, similarity).

### [high/high] dateAdded parse fails for 100% of items — recency weighting silently inert
- **Evidence:** sqlite3 on ~/Zotero/zotero.sqlite: dateAdded values are '2026-05-25 22:48:30'. Live load: corpus[0]['date_added'] and corpus[-1]['date_added'] both == datetime.datetime(1,1,1,0,0). All 495 items have identical datetime.min.
- **Root cause:** load_zotero_corpus parses dateAdded with strptime format '%Y-%m-%dT%H:%M:%S' (zotero_profile.py:235), but Zotero stores dateAdded as space-separated 'YYYY-MM-DD HH:MM:SS' (no 'T'). Every parse raises ValueError and falls to datetime.min, so the sort key (zotero_profile.py:244) is constant and the corpus is NOT sorted newest-first as the docstring claims.
- **Fix:** zotero_profile.py:235 — change format to space separator: `dt = datetime.strptime(date_str[:19], '%Y-%m-%d %H:%M:%S')`. (Stable sort then preserves the SQL ORDER BY dateAdded DESC, so newest-first holds.) Note: this only matters if recency weighting is kept; if you adopt top-k pooling per Bug 1, recency weighting is removed and this becomes cosmetic for the embedding path but still affects any future date-based logic.

### [high/high] Recency decay curve is near-flat — does almost nothing even when dates work
- **Evidence:** Computed on real corpus: weighted score 0.537 vs plain mean 0.538 (zoning), 0.432 vs 0.431 (protein), 0.521 vs 0.521 (ag) — identical to 3 decimals. top-10 decay mass = 0.041 of total.
- **Root cause:** time_decay = 1/(1+log10(i+1)) (zotero_embeddings.py:174). Over 495 items this ranges only from weight[0]=0.0064 to weight[494]=0.0017 (3.7x), and the top-10 newest items hold just 4.1% of total mass. The weighted average is empirically indistinguishable from a plain mean.
- **Fix:** Removed entirely by the Bug 1 top-k fix. If recency must be kept instead, use exponential decay over actual dates (after Bug 2 fix), e.g. weight = 0.5 ** (age_days/365), not a log-rank decay over the full library.

### [high/high] No lexical fallback when embeddings silently return zeros
- **Evidence:** zotero_embeddings.py:160-161 returns [] then [0.0]*len(candidates) on embed failure; newsletter.py:233-239 applies those zeros and never enters the lexical else. The briefing assumed exactly this failure mode (model 'missing'); it is currently masked only because nomic-embed-text happens to be pulled.
- **Root cause:** newsletter.py:232 branches on `if corpus and len(corpus) > 0` for the embedding path and only uses the lexical zotero_author_score/zotero_content_score in the `else`. But compute_zotero_embedding_scores returns [0.0]*n on ANY failure (Ollama down, model missing, np missing — zotero_embeddings.py:138/141/161/169). So a non-empty corpus + failed embeddings yields zotero_boost=0 for every paper with NO fallback. The personalization dies silently with only a _log.warning that never surfaces.
- **Fix:** Make the embedding path detect total failure and fall back. In newsletter.py:233, after `emb_scores = compute_zotero_embedding_scores(curated, corpus)`, add `if not any(s > 0 for s in emb_scores): emb_scores = None` and route to the lexical branch when emb_scores is None. ## external-research  — **ok**

EconSignals fails the three core jobs of a research-feed product because it uses a fixed linear weighted-sum scorer (relevance.py L32-38) instead of a learned, feedback-driven ranker: scores top out at 0.5 with 68% of papers stuck at 0.1, the feedback hook (update_jel_weights) is never wired to any capture mechanism, and there is no social denoising, clustering, "why recommended" explanation, or cadence control. Every comparable product (Scholar Inbox, Semantic Scholar Research Feeds, scite, Feedly/Inoreader) solves these with thumbs up/down retraining over embeddings, cross-source dedup, and transparent explanations. The fixes are well-trodden and mostly low-to-medium effort given the embedding infrastructure already present.

### [high/high] Ranking uses fixed linear weights, not learned personalization — scores compress to 0.0-0.5 and cannot discriminate
- **Evidence:** relevance.py L32-38 (fixed weights); L530-579 score_paper (linear sum, no learned model); DB: SELECT round(relevance_score,1),count(*) FROM papers GROUP BY 1 → 0.0:11, 0.1:389, 0.2:86, 0.3:67, 0.4:7, 0.5:9 (nothing above 0.5, 68% tied at 0.1).
- **Root cause:** relevance.py L32-38 hardcodes weights (W_JEL=0.30, W_KW=0.20, etc.) summed into a [0,1] score. With most papers lacking JEL codes, tracked authors, and India terms, the sum collapses near the recency/prestige floor. The DB confirms it: max relevance bucket is 0.5, and 389/569 papers (68%) sit at 0.1, 86 at 0.2 — the ranker provides almost no separation in the top-of-feed region that matters.
- **Fix:** Adopt the Scholar Inbox pattern (arxiv 2504.08385): replace the hand-tuned sum with a logistic-regression classifier over the existing nomic-embed-text candidate embeddings (already computed in zotero_embeddings.py), trained on user thumbs up/down. Keep JEL/India/recency as a small set of extra features fed into the same classifier rather than as fixed-weight addends. Display a wide signed score (e.g. -100..100) so the top of the feed separates instead of compressing to 0.1.

### [high/high] Feedback loop exists in code but is never wired to a capture mechanism — the system cannot learn
- **Evidence:** relevance.py L626-685 update_jel_weights (no caller); ARCHITECTURE.txt L327-328 EMA alpha=0.05 nudge; DB schema (sqlite_master) has no feedback/rating table; CLAUDE.md command table lists only /scan /brief /deadlines /status.
- **Root cause:** relevance.py:626 update_jel_weights() does EMA on JEL weights given is_interesting, but nothing calls it: there is no thumbs/rating column or table in the schema (papers, social_items have no feedback field; no /feedback command in CLAUDE.md). The only adaptive path is a tiny EMA nudge (alpha=0.05) applied to relevance_score in the newsletter for papers with a positive Zotero boost — a cosmetic adjustment, not learning. Semantic Scholar and Scholar Inbox both treat explicit thumbs up/down AND saved-paper signals as the primary training data.
- **Fix:** Add a `feedback(paper_id, rating, ts)` table and a /rate (or thumbs link in the email) command. Persist saved-to-Zotero and clicked papers as implicit positives. Retrain the L1 logistic ranker on these labels (Scholar Inbox averages 78 positive ratings/user before convergence; active-learning by sampling papers near the decision boundary accelerates cold start). This is the single highest-leverage change: without captured labels, no ranking improvement can compound.

### [medium/high] No 'why recommended' explanation — owner cannot trust or correct the feed
- **Evidence:** relevance.py L549-579 returns only a float; no component breakdown surfaced; Germain UX 2025 and the Scholar Inbox highlight-the-most-relevant-sentence pattern.
- **Root cause:** score_paper returns a single float; newsletter.py renders ranked papers with no per-paper rationale. 2025 recommender-UX consensus: opaque personalization is distrusted and uncorrectable; showing the input signal ('because you saved 3 papers on land rights') is the fastest fix and the precondition for useful thumbs feedback.
- **Fix:** Have score_paper return the top contributing features (e.g. 'JEL O12 match', 'shares author with saved paper X', 'India'), and render a one-line 'Why: ...' under each item in the newsletter. Cheap once score components are already computed.

### [medium/medium] Social stream (2077 items) has no denoising, clustering, or cross-source dedup
- **Evidence:** DB: social_items source counts twitter:1334, mastodon:743; ARCHITECTURE.txt L174 'per-source quotas and snippet deduplication' (lexical only); no cluster/topic column in social_items.
- **Root cause:** social_items stores 1334 twitter + 743 mastodon rows with only an engagement_score; newsletter applies per-source quotas and snippet dedup but no semantic clustering or cross-platform dedup (the same paper announced on Bluesky+Mastodon+Twitter appears as 3 items). Feedly Leo and Inoreader solve volume via cross-source dedup + AI prioritization + an if/then rules engine.
- **Fix:** Cluster social_items by embedding similarity (reuse nomic-embed-text) and by linked paper_id; collapse each cluster to one card with platform badges and a count. Add a lightweight rules layer (mute keyword/handle) mirroring Inoreader. Surface only clusters tied to a paper already ranked highly, so social acts as a signal booster, not a separate noisy stream.

### [low/medium] No saved searches and no cadence (daily vs weekly) control
- **Evidence:** CLAUDE.md /brief is daily-only; profile/identity.md 'Tracked Authors (Add authors here with /track command)' is empty — author-follow is unused; no saved-search table in schema.
- **Root cause:** Watches exist for sensors but there is no user-defined saved-search/topic-follow abstraction, and the newsletter is daily-only. Researcher app (follow journals/authors/keywords/topics, exclude terms) and Scholar Inbox (daily/weekly toggle + catch-up digest) both treat these as core. For an abandoned tool, a weekly cadence alone would cut perceived noise sharply.
- **Fix:** Add saved searches (name + query + include/exclude terms) as first-class rows feeding both ranking features and a per-search digest section; add a daily/weekly cadence flag and a 'catch-up digest' that surfaces only the top-N since last open.
